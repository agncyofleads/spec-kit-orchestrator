# Full Path

Follow this path for project initialization or a complete SDD cycle. Constitution is created only when initializing a project. Later amendments require an explicit decision; do not silently revise it.

## Sequence and transitions

1. **Constitution (initialization only):** for a genuinely new project, first ask the operator for rules, principles, and constraints; create/populate the initial Constitution only from the answers. Then stop and request the desired functionality. This is an information handoff, not an approval gate. For an existing project, respect its current Constitution; make no amendment absent an explicit decision. A pre-existing file alone does not prove that a Constitution operation was performed.
2. **Specify:** after receiving the operator's feature description, define only that functionality and why. Preserve the user's intent and create the authoritative `spec.md`; do not invent or extend the feature. Then stop before Clarify and invite the operator into general functional clarification. This is an information handoff, not an approval gate.
3. **General clarification:** conduct the functional clarification dialogue with the operator, resolve ambiguities and incorporate only agreed decisions, corrections, or expansions into the Spec. If no ambiguity remains, record that disposition as the completed clarification activity. A canceled/unanswered question is not completion; do not advance.
4. **UX/UI clarification (conditional):** perform only if the specification includes interface, UX, or human interaction. Otherwise skip.
5. **Integral-semantic Spec review:** perform the single read-only technical review of Spec completeness, coherence, clarity, verifiability, ambiguity, and alignment with Constitution/relevant artifacts. On technical FAIL, report blockers, evidence, impact, and owner; stop without a human approval request until the Spec is corrected and the same review is repeated. On technical PASS, summarize the Spec's functional behavior, rules, inputs, outputs, validations, and exceptions for the operator to compare with their intent; stop for explicit human PASS/FAIL. On explicit PASS, continue to Plan in the same conversation; `/sdd-approve` and `/sdd-resume` are not required. On human FAIL, correct the Spec and repeat this same review.
6. **Plan:** define the technical how, aligned with approved Spec. Do not move implementation design into Specify.
7. **Post-Plan architectural review:** perform the sole read-only Review of technical soundness and traceability to approved requirements. Classify FAIL findings: objectively Plan-remediable issues are corrected by the Plan owner and this same Review is repeated, without an intermediate user-facing result or gate. Continue without a fixed retry count only while corrections make evidence-backed progress within approved behavior; stop and report unresolved blockers if ownership is unclear, no supported correction exists, findings repeat without a new resolution path, or remediation oscillates. If resolving a finding requires a functional decision, suspend for the operator's Specify/Clarify input and do not alter approved behavior unilaterally. Any material invalidation of an approval returns the workflow to the earliest affected phase and its review and human gate. Only on PASS or PASS WITH WARNINGS, present the architecture explanation and extraction, including the raw Plan tree, path responsibilities/relationships, and actual-versus-proposed path status, then request the single human approval. Do not proceed to Tasks before approval.
8. **Tasks:** generate the complete initial task decomposition and its tests from approved artifacts.
9. **Test Scope Review:** refine tests. Separate automatable technical tests strictly from operational tests that only a human can perform. Check traceability, proportionality, dependencies, and legitimate execution timing. Suspend for conversational approval; do not create a review record.
10. **Tasks refinement:** reduce excessive granularity, improve dependencies, optimize possible parallelism, and establish the executable DAG.
11. **Human DAG review:** explicitly verify Plan-to-Tasks/DAG coverage; identify omissions; explain tasks, dependencies, parallelism, and expected results. Suspend for human PASS.
12. **Analyze → remediation → reanalysis:** delegate the read-only cross-artifact review. The Coordinator routes each finding to its existing artifact/task owner, permits only objective corrections within approved contracts, and reruns the same review after each correction. Continue without a fixed round limit only while evidence-backed progress is being made. Suspend for functional choices or material approval invalidation; stop without PASS when ownership is unresolved, corrections are unsupported, or findings cycle/oscillate. A supported Analyze PASS is necessary but does not replace any still-required human approval.
13. **Implement:** only after Analyze PASS and confirmation that required human approvals and the DAG remain valid, execute tasks with specialized sessions, automatically only if an implementation mechanism is actually available. Parallelize only where the approved DAG permits. Do not imply that an orchestration engine exists.
14. **Converge:** perform a global final implementation review. Route gaps to the correct owner, remediate, and repeat until PASS. Do not claim PASS before the review supports it.
15. **Operational human tests:** after Converge PASS, the operator performs the tests designated exclusively human. Record only actual outcomes; unresolved failure blocks acceptance.
16. **Git closeout:** only after human operational acceptance and explicit authorization. Without both, stop before commit, push, or other closeout.

## Suspension and remediation

The Spec and Architectural Reviews first produce their technical verdicts. Those verdicts precede and never substitute for the separate explicit human approvals required at those gates. At each human gate, present the required explanation and evidence, then stop. Do not treat silence, inferred intent, or an earlier approval of a different artifact as approval. A failed review is remediated by its owner; repeat the failed review before advancing. Preserve warnings and unresolved decisions rather than silently waiving them.

Do not add a Specify review, Plan review, checklist, or per-wave review checkpoint. The named reviews and approvals above are the workflow's gates; do not add redundant human gates.
