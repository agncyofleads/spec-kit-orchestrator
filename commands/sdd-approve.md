---
description: Validate and acknowledge an explicit human decision for one identified SDD gate.
agent: sdd-coordinator
---

This command is optional. A plain explicit decision in the active gate conversation is sufficient; do not require `/sdd-approve` to resume an SDD phase. If invoked, validate the decision against the currently pending gate, conversation, authoritative artifacts, and applicable `sdd-workflow` policy. Input format: `gate=<spec-review|architecture-review|test-scope|dag-review|operational-acceptance|git-authorization> decision=<gate-specific outcome> scope=<exact artifact, decision, or action>`. Supplied decision: $ARGUMENTS

Accept only one of the listed gates when it is currently pending, with matching scope, required evidence, prerequisites, and gate-specific outcome. Spec/DAG use `PASS`; architecture and Test Scope use `APPROVE`; operational acceptance uses `ACCEPT` with reported observed human-test outcomes; Git authorization uses `AUTHORIZE` only with its exact operation and target. `REJECT` may be used for any pending gate. Reject missing, ambiguous, stale, out-of-scope, or unsupported decisions. Never treat this command's invocation, a tool permission approval, silence, or an approval for another gate as approval.

Constitution establishment remains part of `/sdd-init` for a new project. An amendment requires explicit human authorization naming its exact scope in the owning workflow conversation; it is not a gate and must not be accepted under `/sdd-approve`. Do not amend Constitution without that authorization.

For a valid `spec-review` PASS, continue directly to Plan in the same coordinator conversation after reporting the validated decision; do not ask the operator to run `/sdd-resume`. For valid human FAIL, route the requested correction to the Spec owner and repeat the same review before Plan. For a valid `architecture-review` APPROVE, continue to Tasks only after the technical Review has passed and the complete architecture explanation/extraction has been presented. On architecture REJECT or requested changes, route objective technical corrections to the Plan owner and repeat the same Review under the evidence-backed, no-fixed-retry policy in `sdd-architecture-review`; if changes require a functional decision, return to Specify/Clarify rather than altering approved behavior. For other gates, permit only their documented next transition. No durable approval ledger or workflow-state persistence is available; do not claim one. A `git-authorization` decision, if explicitly requested, is valid only after operational acceptance and must name the exact requested Git action and target; this command never runs Git or authorizes any other action. Follow-up work still requires its own scope and tool permissions.
